RFQ BID TRACKER - SPEC
======================

User:     Israel Blackman, Discover Group (Brooklyn, NY)
Purpose:  See each request at a glance and decide whether or not to bid.
Principle: Include all information needed for a bid / no-bid decision, and nothing extra.
Status:   Built and running on LIVE data: NYC City Record, SAM.gov and 28 state portals
          (section 3). The page never shows made-up data: no feed = "No data". (A labelled
          sample dataset loads only on the public github.io demo; see sample-data.js, section 5.)


1. MAIN VIEW - TABLE COLUMNS
----------------------------
Ten columns, left to right. Each is sortable except RFQ doc and Details. (The per-row
Status dropdown was removed; bid tracking lives in the separate bidding app.)

 #  Column          Notes
 1  Request         Title of the request (agency shown beneath). ALL-CAPS titles from
                    agencies are tidied to Title Case (acronyms kept upper case).
 2  Category        Type of work. NYC: City Record category. SAM.gov: "NAICS <code>". States: the
                    portal's category (UNSPSC codes become a readable name).
 3  Eligibility     Chips listing everything the RFQ requires to bid (Israel decides); "Not read" if unknown.
                    Chips come from the notice's requires[] plus items found in the notice text
                    and Details notes (licence, clearance, background check, prequalification,
                    set-aside, vendor registration, restriction). Colors: red = gate (notice
                    requirements, restriction, prequalification, set-aside); amber = effort
                    (vendor registration, anything the notice says can be waived, e.g.
                    "Prequalification required (unless waived)"). Gate-type bid
                    factors (licence, clearance, background check, minimum experience, bid
                    bond / guarantee, bonding capacity) also appear here; keyword-only matches
                    are "Possible: ..." chips. Performance bonds, insurance, pre-bid and local
                    preference stay under Bid factors only.
                    The app does NOT judge eligibility: there is no company profile
                    and no yes / no result (DECIDED, see 2a). Sortable. AI-read rows
                    say "AI-extracted, please verify."
 4  Posted          Date the request was posted.
 5  Due date        Bid due date plus due time and time zone. Due dates more than 3 years
                    out are treated as placeholders: shown as "No real due date".
 6  Days left       Days from today to the due date. "Closed" if past, a dash if no real
                    due date. Colored: 7 or fewer = red, 14 or fewer = orange, else green.
 7  Level           Federal / State / Local badge.
 8  RFQ doc         "Open RFQ" link to the solicitation (NYC City Record page or SAM.gov
                    notice, or the state portal's page). Only https links are
                    opened; anything else becomes a dead link.
 9  Est. value      Dollar value, always labelled with where it came from, in this order:
                    a) Published by the agency (contract amount in the notice).
                    b) Stated in the notice: amount read by AI, with the quoted sentence
                       under "Where from". Only kept if the quote really contains the
                       amount. Flagged "AI-extracted, please verify".
                       Both fetchers ALWAYS try (b) before any estimate: a keyword pass
                       (stated-amount.js, no key needed, cue phrase + no conflicting
                       figures) and then the AI read when ANTHROPIC_API_KEY is set.
                    c') Federal (SAM.gov) notices: same kind of estimate from USAspending.gov
                       awards (last 3 years, purchase/delivery orders and contracts) with the
                       same NAICS code, matched on title keywords, else all in that NAICS;
                       needs at least 5 awards. Run by fetch-sam.js; or `node sam-estimates.js`.
                    c'') State notices: same USAspending estimate, using a NAICS prefix mapped
                       from the notice's UNSPSC codes or a NAICS stated in the text; labelled a
                       rough guide. Run by fetch-states.js.
                    c) Estimate from similar past awards (NYC): median with a
                       25th-75th percentile range, from competitively bid City Record
                       awards of the last 3 years (renewals, amendments, noncompetitive
                       excluded). Tiers: same agency + category + title keywords;
                       same category (any agency) + keywords; same agency + category
                       with no keyword match ("broad estimate"). Needs at least 3
                       awards. "How estimated" lists the method and 5 recent examples.
                    d) "Not published" when none of the above exists.
                    DEFAULT SORT: descending by this value; unknown values last.
10  Details         ONE merged column, same order in every cell. Top to bottom:
                    1) status chips (Amended, warnings), only when present
                    2) labeled rows, left out when empty: "Region" (small muted label;
                       kept because Level shows only Federal / State / Local),
                       "Terms" (plain requirement chips, e.g. selection method,
                       mandatory pre-bid). The "Bid factors" box (see below) is in the
                       Eligibility cell.
                    4) scope summary, cut at 220 characters with Show more / Show less
                    5) "Show all requirements (n)" toggle that opens a full-width row of
                       the key "shall" statements with section/page refs and a link to
                       the full RFQ. Only shown when shall[] is not empty.
                    AI-read rows are labelled "AI-read, verify".
                    Rows whose documents were not read show a "No document access" badge
                    and a note saying why (e.g. the portal forbids automated reads, or needs
                    a login), so a thin row is not mistaken for a complete one.

Bid factors (box at the top of Details)
 Chips for facts that commonly decide bid / no-bid. Detected by keyword (FACT_RULES in
 index.html) from the scope, "shall" text, requirement chips and restriction. Hover a chip
 to see the source sentence. Colors:
   red   = gate: TSA-checked workers, security clearance, background checks /
           fingerprinting, license / certification
   amber = cost / effort: bonds, insurance minimums, prevailing / living wage, mandatory
           site visit / pre-bid, 24/7 or after-hours, proposal / bid guarantee
   blue  = info: local / in-state preference, past performance / references, multi-year term
 Bonds, pre-bid meetings and background checks are chips, not dedicated fields (decided).
 SPLIT (decided): Eligibility = things that disqualify a bid if he lacks them (gates); Bid factors
 in Details = cost / effort / attractiveness. Gate factors (TSA-checked workers, security
 clearance, background checks, license / certification, minimum experience, bid bond / bid
 guarantee, bonding-capacity minimum) are flagged gate in facts.js and listed in the
 Eligibility column, not in the Bid factors box. When only keyword-matched (no read of the
 documents) they show as a softer dashed "Possible: ..." chip. Cost / info factors stay in
 Details: performance / payment bonds, insurance, prevailing wage, mandatory site visit /
 pre-bid (a date-bound event, so Details), 24/7, local preference, past performance, term.

Toolbar and behavior
 - "Filter by" column filters (one panel per column, with value lists, ranges and dates);
   active filters show as removable chips above the table. The value counts in each list
   follow the Hide closed checkbox. The State list covers every state that has data, plus
   US = federal and NYC; a state whose last fetch failed or was partial is marked.
   The free-text search box was REMOVED from the toolbar; the Search section below
   describes the query syntax still in the code, which has no input box right now.
 - Refresh control: a pill toggle All / Failed / Specific plus a Refresh button.
   Specific opens a multi-select of portals (Federal, NYC, all states, or single states).
   The button calls POST /api/refresh with ?failed=1 or ?portal=sam,nyc,state:NY (comma list).
   An unknown portal or state code gets 400 instead of an empty run. Failed re-runs only the
   failed states. The refresh banner names the sources and states being retried.
 - Fetch-health banner above the table: red when a state's last fetch failed (older notices are
   still shown, with the date of the last good fetch), amber when partial, and a notice if
   live-states.js did not load. Hidden when every state fetched fine.
 - "Hide closed" (on by default): hides bids whose due date has passed; untick to show them.
 - "Hide flagged" (on by default): hides notices with a warning, i.e. a placeholder
   deadline (2099 or later, or more than 3 years out) or posted over a year ago.
 - Count line: "n of N requests", source(s) and when the data was last updated.
 - The long "shall" list is not loaded with the page: it is fetched per notice from the
   service (/shall/<id>) when "Show all requirements" is opened.
 - Paging: requests are drawn 100 at a time, with "Show N more" and "Show all" buttons, so filtering
   and resizing stay fast. The count line still reports the full match count. Changing a filter or
   the sort goes back to the first 100.
 - Filters, sort, open rows and scroll position are kept across the automatic reload after a refresh.
 - Banners: Refreshing (shows the step and how many states are done), first-install notice, a
   warning when the data is over 36 hours old (from dataAsOf), and an offline message that says how
   old the data is. The page explains when it is served by something other than the RFQ service.
 - Click a header to sort; click again to reverse.
 - Narrow screens (900px or less): each request becomes a labelled card.

Search (query syntax in the code; no search box in the toolbar at present)
 Free-text words must all match (AND) anywhere in the request, including dates and values.
 Plus optional structured pieces:
   numbers:   "value > 300k", "value 100k-500k", "days left <= 7", "days left: 22".
              Field names: value/price/amount/cost, days left, due/ends/closes/deadline,
              posted/date. Operators: > < >= <= = != ; k/m/b suffixes; ranges.
   dates:     "due < 2026-12-31", "posted >= 2026-10-01" (a bare date means due date).
   column:    "level: local", "category: construction", "agency: ...",
              "request: ...", "region: ...", "eligibility: <requirement>".
   "no due date" finds placeholder or missing deadlines.
   A bare column name (e.g. "level") does not narrow the results.


2. OPEN QUESTIONS / POSSIBLE GAPS (to confirm with Israel)

 a. Eligibility: DECIDED - the column only lists what each RFQ requires; Israel judges.
    The company-profile comparison (yes / no per request) is SKIPPED: not needed, and

    "eligibility: determined / yes / no" searches were removed. The column sorts by

    Answer: no.
 b. Bonds, pre-bid meetings, background checks: DECIDED, shown as Bid factors chips
    (section 1).
 c. Bid status: REMOVED from this app. Tracking which requests are pursued (interested / bidding /
    submitted / passed) is handled by the separate bidding app fed from the JSON feed.
 d. (Dropped: contact and submission method are not a feature of this app.)
 e. Contract length: the term of the contract (not the same as the bidding window).
 f. Amendments: should the app notify him (or show what changed) when a solicitation is
    amended after he has looked at it? Today only an "Amended" chip exists, and the
    feeds do not set it.
 g. Regions and categories: DECIDED - all USA, all categories. Anything out of area
    (outside the USA) or out of scope is HIDDEN automatically. BUILT for out-of-area only (SAM.gov: place of performance
    country not US is skipped in fetch-sam.js; notices already cached stay until they close).
    Out of scope NOT BUILT. OPEN:
    what counts as out of scope when every category is wanted (e.g. a work type
    Discover Group does not do)? Needs Israel's definition.
 h. Sources: DECIDED - no source priority; all are wanted. Order the list by estimated
    value, highest first (already the default sort). States that forbid automated reads
    and offer no feed or email digest stay parked (state-feed-requests.md,
    state-sources-survey.md).
 i. "Shall" requirements: DECIDED - scope summary under each request plus an expandable
    list of key "shall" statements, each with its RFQ section/page. Now filled by the AI
    read (3-5 key points per notice, quoted near-verbatim) for NYC and SAM.gov rows
    where the notice has enough text. OPEN: how many statements are enough, and whether
    SAM.gov attachments (the full solicitation PDFs) should be read, not just the
    notice description.
 j. AI reading and billing: the AI read (ai-extract.js, used by fetch-nyc.js and
    fetch-sam.js) uses Claude Haiku via an Anthropic API key (ANTHROPIC_API_KEY, set in
    the environment, never in a file). API usage is billed separately from a Claude chat
    plan. Each run prints and logs (ai-usage.log) calls, tokens and an ESTIMATED cost;
    the Anthropic Console is the authoritative bill. Results are cached in ai-cache.json
    by hash of the notice text, so unchanged notices cost nothing on the next refresh
    (entries unseen for 60 days are dropped; delete the file after changing a prompt).
    Without a key, NYC and SAM rows simply have fewer Bid factors chips and no AI value.
    Billing now (2026-11-11): the account is on a $20 prepaid plan that auto-reloads $20
    when the balance reaches $5, so each reload covers about $15 of use. Estimated one
    reload every 3 to 8 months at $2 to $5 a month (projection; see anthropic-key-setup.md).
    The key is in the local .env (git-ignored).
    OPEN: who owns the Anthropic account and pays long term? Where does the key live once
    refreshes run on a schedule on the server?
 k. "Interested" follow-up: DROPPED (no statuses here). The feed carries rfqUrl only.
 l. Multiple users: no longer applies to this app (no statuses, no logins). 
 m. Hosting: OPEN - to discuss with Israel, to keep the information safe. Assumed: own
    server, multiple logins. Existing server or a new one? Recommendation: use the
    existing server only if it is well maintained (patched, backed up, HTTPS) and run
    the app as its own low-privilege user or in Docker; if it is old, neglected or hosts
    something important, a separate VPS ($5-10/month) is cheaper than the risk. Also
    open: Linux or Windows server.
 n. Refresh trigger: DECIDED. Fetchers run automatically once a day, on the first check or
    wake after 5:00 local time (REFRESH_MORNING_HOUR changes the hour); after a wake the service waits
    45 s for the network. A source still failing is retried up to 3 times, 20 minutes apart. On first
    install every source runs at once. A fetcher frozen by sleep is stopped after FETCH_TIMEOUT_MIN
    (45) and retried. Network calls (Anthropic, SAM.gov, USAspending) have their own request
    timeouts, and the AI cache and SAM cache are saved after every call, page and notice, so a
    killed run keeps the paid work; live-nyc.js and live-sam.js are written via a temp file and
    rename so a crash never leaves a half-written file. A failed USAspending estimate lookup is
    retried next run; if the NYC awards query fails only the similar-award estimates are skipped.
    The AI cache file (ai-cache.json) must persist on the
    server between runs, otherwise every notice is re-read and re-billed. Estimated AI
    cost is a few cents a day, roughly $1 to $3 a month (a projection, not a measurement;
    check ai-usage.log and the Anthropic Console). The earlier figure of about 50 cents
    a month predates the state portals. SAM.gov limits requests per key (a personal key is
    commonly about 10 a day; an entity-linked key about 1,000 - check the account page).
    A higher limit would allow refreshing more than once a day, checking amendments on
    Interested notices, and pulling attachments for the AI summaries.
 o. Privacy: the feed data is not private, so the API has no authentication, the service listens on
    127.0.0.1 by default (HOST must be set to expose it), and the page is served only on the service
    machine. No bid statuses are stored here. Agency text must be shown as plain text,
    never run as code: CHECKED 2026-11-09 with real data flowing in. Every field is HTML-escaped,
    links must be https (otherwise a dead "#"), and the service sends a Content-Security-Policy.
    Tested with hostile text in every field: shown as literal text, nothing ran. AI reading of attachments
    must only fill fields and be labelled "AI-read, verify".
    The one exception to "no authentication" is POST /api/refresh, because it spends SAM
    quota and Anthropic money: it is accepted only from the service machine itself (loopback),
    and never from a cross-site browser request (an Origin that differs from Host is refused,
    403). To allow a remote caller, set REFRESH_TOKEN in .env; the caller then sends
    "Authorization: Bearer <token>" (401 if missing or wrong). Reads (GET) stay open.


3. DATA INTEGRATION
-------------------
How it works: node fetchers write generated live-*.js files (git-ignored); server.js runs them,
merges the result into data/state.json, serves it as JSON (FEED.md) and serves the page
(index.html), which loads live-sam.js, live-nyc.js and live-states.js and merges them. The
data shape is documented at the top of data.js. Fetchers run once a day, on the first
check or wake after 5:00 local time (REFRESH_MORNING_HOUR); sources that still fail are
retried up to 3 times, 20 minutes apart (RETRY_AFTER_MIN, RETRY_MAX). A failed fetch
leaves the old live file untouched, so old data stays; a failed state keeps its last notices
and is flagged on the page and in /api/status.

 - NYC City Record (fetch-nyc.js): LIVE. Open Procurement solicitations from NYC Open
   Data, no key needed. Read by paging the Socrata API (5,000 rows a page, transient errors
   retried, so no rows are silently dropped). Optional AI read (needs ANTHROPIC_API_KEY): stated amount,
   requires, scope, key "shall" points. Then similar-award value estimates.
   Run: node fetch-nyc.js [--max 500]  (--max = most open solicitations loaded)
 - SAM.gov Opportunities (fetch-sam.js): LIVE. Solicitations and combined
   synopsis/solicitations posted in the last 30 days. Needs SAM_API_KEY (free; environment
   only). Quota-aware (SAM_DAILY_BUDGET, default 10 requests a day): each description is read
   once, and a backlog resumes the next day. Optional AI read as above.
   Run: node fetch-sam.js [--days 30 --max 5000 --budget N]  (--max = most new notices added per run)
 - State portals (fetch-states.js): LIVE, 28 adapters, one per state in states/ (a failing
   state does not stop the others; one retry pass after a pause):
     DE IN IA LA MS SC ID VT TX (TxDOT lettings only) RI NY WY KS FL NE WV MO SD OK AR CO AK HI,
     plus NV NJ OR IL MA via the shared Periscope adapter (states/bso.js).
   Each notice needs a title, https link and due date, else it is dropped. Then USAspending
   value estimates and the AI read of the notice page and attachments (needs
   ANTHROPIC_API_KEY; capped at STATE_MAX_READS = 60 new reads per run, soonest deadline
   first; earlier reads are reused; a notice whose listing changed, i.e. an amendment, is re-read). Portals that forbid reads or need a login are marked
   noPageReads and show a "Not read" note. Run: node fetch-states.js [DE NV ...]
   Per-state status and the reasons for parked states: state-sources-survey.md,
   state-fetch-status.pdf, state-feed-requests.md.
 - Pennsylvania (states/pennsylvania.js): written but NOT registered (it is not in the
   ADAPTERS list in fetch-states.js, and a state waiting for setup is not retried). PA forbids
   automated reads; the only route is DGS's eAlert emails, read over IMAP (read-only) from a
   dedicated Gmail account (PA_GMAIL_USER, PA_GMAIL_APP_PASSWORD). Waiting on the Google app
   password; until it is registered PA shows nothing.
 - Not started: SAM.gov Entity API (vendor registrations), DIBBS and eBuy (need logins or
   scraping). Add one at a time. Rule: only fully automatic sources are kept; manual CSV or
   .eml routes were removed.
 - Secrets and generated files stay out of git (.gitignore): .env, keys, live-*.js, data/,
   ai-usage.log, ai-cache.json, sam-cache.json, sam-quota.json, logs.

Things that trip up newcomers (from notes)
 - Deadlines are date, time and time zone, plus the agency's clock rules.
 - Solicitations change by amendment: diff and notify.
 - An RFQ may go only to GSA Schedule holders or a short list of vendors.
 - Lowest price does not always win; technical acceptability and responsibility count.
 - Past performance / CPARS ratings matter to repeat buyers.
 - Sources-sought notices are early signals.
 - Teaming agreements and subcontracting are central; model partners.


4. FILE MAP - WHAT EACH FILE DOES
---------------------------------
Service and page
 server.js           The one running process. Loads .env, runs the fetchers (24 h rule, wake
                     detection), ingests results, and serves HTTP: the page and
                     its scripts (this machine only), /api/health, /api/status (incl.
                     per-state health), /api/rfqs, /api/rfqs/<id>, POST /api/refresh,
                     /shall/<id>. Builds a slimmed live-states.js for the page. --once =
                     one refresh then exit.
 service/feed.js     Reads the live-*.js files, normalizes every notice to the feed schema,
                     keeps data/state.json (seq cursor, active flag, 90-day tombstones) and
                     answers feed queries. Lists the sources and their fetch scripts.
 index.html          The whole UI: table, search, filters, sorting, fetch-health banner, card
                     layout on narrow screens. Escapes all text, links https only.
 facts.js            Bid-factor keyword rules (FACT_RULES), shared by the page and server.
 data.js             Documents the notice data shape (comment only; no data).
 sample-data.js      Invented demo rows, loaded only on *.github.io.
 package.json        npm run refresh; Node 18+, no dependencies.
 .claude/launch.json Local preview config for the editor (git-ignored).

Fetchers and helpers (project root)
 fetch-nyc.js        NYC City Record -> live-nyc.js (AI read, similar-award estimates).
 fetch-sam.js        SAM.gov -> live-sam.js (quota-aware, set-aside mapping, AI read).
 fetch-states.js     Runs the state adapters -> live-states.js (estimates, document reads,
                     retry pass, carry-over of failed states, backups in data/backups).
 sam-estimates.js    USAspending similar-award estimates (federal and state NAICS lookups).
 stated-amount.js    Keyword pass that finds a contract amount stated in a notice (no key).
 ai-extract.js       Claude Haiku reader: requires, scope, "shall" points, stated amount.
                     Validates output strictly, caches in ai-cache.json (saved per call), logs cost. Request timeout; a stated amount must match as a whole figure. Retries 429/5xx/network
                     errors with backoff; a bad key or retired model id stops the run with one message.

State adapters (states/)
 <state>.js          One adapter each { code, name, fetch() } for the portals listed in
                     section 3. A header comment in each says how that portal is read.
 bso.js              Shared Periscope "bso" adapter for NV, NJ, OR, IL, MA.
 common.js           Shared helpers: http with retry, request counting, text cleaning, time zones.
 docs.js             Fetches a notice's page and attachments (PDF, Word, zip) for the AI read.
 zip.js              Minimal ZIP/.docx reader used by docs.js.
 unspsc.js           UNSPSC code -> readable category and NAICS prefix.
 pennsylvania.js     Gmail eAlert reader (not registered; see section 3).

Docs and notes

 FEED.md             The JSON feed API for client apps.
 anthropic-key-setup.md   Steps to create and fund the Anthropic key (no secrets).
 state-sources-survey.md  Survey of every state's source and its status.
 state-feed-requests.md   Feed-request emails to states that forbid automated reads.
 rfq-bid-tracker notes.md Scratch notes (not part of the app).
 make-status-pdf.py  Regenerates state-fetch-status.pdf (needs reportlab).
 state-fetch-status.pdf  Per-state fetch status report.
